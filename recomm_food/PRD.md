# PRD: 냉장고 재료 기반 요리 추천앱

## Problem Statement

냉장고에 재료는 있는데 무엇을 만들어야 할지 모르겠다. 레시피 사이트에서 검색하면 내가 가진 재료가 아니라 요리 이름으로 찾아야 하고, 막상 레시피를 열어보면 없는 재료가 여러 개 들어 있어 만들 수 없는 경우가 많다. "지금 가진 재료로 바로 만들 수 있는 요리"와 "한두 개만 사 오면 되는 요리"를 한눈에 알고 싶다.

또한 이 앱은 AI 교육 과정의 과제/포트폴리오용 데모로, 시연 중 안정적으로 동작하고 RAG(검색 증강 생성) 구조를 명확히 보여줄 수 있어야 한다.

## Solution

사용자가 냉장고에 있는 재료를 텍스트(자동완성 태그)로 입력하면, 앱이 직접 구축한 레시피 데이터셋에서 후보를 검색하고, 보유 재료와의 일치 정도를 정확히 계산해 순위를 매긴 뒤, LLM이 "왜 이 요리를 추천하는지"와 "부족한 재료를 무엇으로 대체할 수 있는지"를 설명해 준다.

결과는 두 묶음으로 보여준다.

- **지금 바로 만들 수 있어요**: 부족한 주재료 0개
- **1~2개만 더 있으면 돼요**: 부족한 주재료 1~2개 (부족 재료 명시)

소금·간장·식용유 같은 기본 양념은 집에 있다고 가정하며, 사용자가 사이드바에서 조정할 수 있다.

## User Stories

1. 사용자로서, 냉장고에 있는 재료를 텍스트로 입력하고 싶다, 그래야 복잡한 절차 없이 바로 추천을 받을 수 있다.
2. 사용자로서, 재료를 입력할 때 자동완성 목록에서 고르고 싶다, 그래야 오타나 표기 차이 때문에 추천이 누락되지 않는다.
3. 사용자로서, "달걀"이라고 입력해도 "계란"이 들어간 레시피가 나오길 원한다, 그래야 내가 쓰는 표현과 상관없이 정확한 결과를 얻는다.
4. 사용자로서, 입력한 재료를 태그 형태로 보고 개별적으로 삭제하고 싶다, 그래야 잘못 넣은 재료를 쉽게 고칠 수 있다.
5. 사용자로서, 재료 입력 후 버튼 한 번으로 추천을 받고 싶다, 그래야 사용 흐름이 단순하다.
6. 사용자로서, 지금 가진 재료만으로 만들 수 있는 요리를 따로 보고 싶다, 그래야 장을 보지 않고 바로 요리할 수 있다.
7. 사용자로서, 재료가 1~2개만 부족한 요리도 보고 싶다, 그래야 조금만 사 오면 만들 수 있는 선택지를 알 수 있다.
8. 사용자로서, 각 추천 요리에서 부족한 재료가 정확히 무엇인지 보고 싶다, 그래야 무엇을 사야 할지 안다.
9. 사용자로서, 소금·설탕·간장·식용유 같은 기본 양념은 입력하지 않아도 되길 원한다, 그래야 입력이 번거롭지 않다.
10. 사용자로서, 기본 양념 목록에서 우리 집에 없는 양념을 체크 해제하고 싶다, 그래야 실제 상황에 맞는 추천을 받는다.
11. 사용자로서, 추천 요리가 왜 추천되었는지 짧은 설명을 보고 싶다, 그래야 결과를 신뢰할 수 있다.
12. 사용자로서, 부족한 재료의 대체 재료 제안을 받고 싶다, 그래야 장을 보지 않고도 만들 수 있는지 판단할 수 있다.
13. 사용자로서, 각 요리의 조리 시간과 난이도를 보고 싶다, 그래야 상황에 맞는 요리를 고를 수 있다.
14. 사용자로서, 추천 요리의 재료 목록(양 포함)과 조리 순서를 보고 싶다, 그래야 앱만 보고 바로 요리할 수 있다.
15. 사용자로서, 레시피 상세를 카드에서 펼쳐 보고 싶다, 그래야 결과 목록이 깔끔하게 유지된다.
16. 사용자로서, 추천 결과가 보유 재료 일치율이 높은 순으로 정렬되길 원한다, 그래야 가장 적합한 요리를 먼저 본다.
17. 사용자로서, 만들 수 있는 요리가 하나도 없을 때 안내 메시지를 보고 싶다, 그래야 앱이 고장 난 것이 아님을 안다.
18. 사용자로서, 재료를 하나도 입력하지 않고 추천을 누르면 입력을 요청하는 안내를 받고 싶다, 그래야 무엇을 해야 할지 안다.
19. 사용자로서, 추천 결과가 몇 초 안에 나오길 원한다, 그래야 시연과 실사용이 답답하지 않다.
20. 사용자로서, 같은 재료를 넣으면 같은 요리 목록이 나오길 원한다, 그래야 결과를 신뢰할 수 있다.
21. 사용자로서, 카테고리(밥, 국/찌개, 면, 반찬, 일품, 분식/간식, 양식)를 보고 싶다, 그래야 식사 구성에 맞게 고를 수 있다.
22. 발표자로서, 앱이 존재하지 않는 레시피나 없는 재료를 지어내지 않길 원한다, 그래야 시연 중 신뢰도가 떨어지지 않는다.
23. 발표자로서, 추천 근거(일치 재료 수/부족 재료)가 화면에 숫자로 보이길 원한다, 그래야 RAG + 규칙 기반 하이브리드 구조를 설명하기 쉽다.
24. 발표자로서, 인터넷 레시피 API 장애와 무관하게 앱이 동작하길 원한다, 그래야 시연이 외부 요인으로 실패하지 않는다.
25. 개발자로서, 레시피 데이터를 JSON 파일 하나로 관리하고 싶다, 그래야 레시피 추가·수정이 쉽다.
26. 개발자로서, 레시피 데이터가 바뀌면 벡터 DB를 다시 구축하는 명령을 한 번에 실행하고 싶다, 그래야 데이터와 인덱스가 어긋나지 않는다.
27. 개발자로서, OpenAI API 키를 환경변수에서 자동으로 읽길 원한다, 그래야 키를 코드나 파일에 노출하지 않는다.
28. 개발자로서, API 키가 없을 때 명확한 오류 메시지를 보고 싶다, 그래야 설정 문제를 빨리 해결한다.
29. 개발자로서, LLM 설명 생성이 실패해도 추천 목록 자체는 보이길 원한다, 그래야 LLM 장애가 앱 전체 장애로 번지지 않는다.
30. 개발자로서, 추천 로직을 LLM·벡터 DB 없이도 테스트하고 싶다, 그래야 비용 없이 빠르게 검증할 수 있다.
31. 개발자로서, 재료 동의어를 별도 사전으로 관리하고 싶다, 그래야 표기 차이를 코드 수정 없이 보완할 수 있다.
32. 개발자로서, 기본 양념 목록을 설정값으로 관리하고 싶다, 그래야 정책 변경이 쉽다.

## Implementation Decisions

### 범위와 대상
- 과제/포트폴리오 시연용 단일 사용자 데모. 로그인, 회원, 배포, 재고 영구 저장은 하지 않는다.
- 재료 입력은 텍스트(자동완성 멀티셀렉트) 방식만 지원한다.

### 기술 스택
- UI: Streamlit
- LLM 오케스트레이션: LangChain
- LLM: OpenAI `gpt-4o-mini` 급 모델 (설명 생성 전용)
- 임베딩: OpenAI `text-embedding-3-small`
- 벡터 DB: Chroma (로컬 영속 저장)
- API 키: 사용자 환경변수 `OPENAI_API_KEY`에 이미 등록되어 있으며(확인 완료), 코드는 이를 자동으로 읽는다. `.env` 파일은 사용하지 않는다.

### 레시피 데이터
- 외부 API(식약처 레시피 DB)는 사용하지 않는다. 프로젝트의 `data` 디렉토리에 `recipes.json`으로 직접 작성한 레시피 100개를 둔다.
- 한식 가정식 위주로 하되 간단한 양식·분식을 포함한다. 별도 사람 검수는 하지 않는다.
- 재료명은 작성 시점부터 표준 재료명(canonical name)으로 통일한다. 따라서 데이터 적재 시 LLM 기반 재료 정규화 단계는 필요 없다.
- 주재료와 양념을 처음부터 분리해 저장한다.
- 레시피 스키마(대화에서 합의한 형태):

```json
{
  "id": "r001",
  "name": "김치볶음밥",
  "category": "밥",
  "cook_time_min": 15,
  "difficulty": "쉬움",
  "servings": 1,
  "main_ingredients": [{"name": "김치", "amount": "1컵"}],
  "seasonings": [{"name": "식용유", "amount": "1큰술"}],
  "steps": ["김치를 잘게 썬다.", "..."],
  "tags": ["자취요리", "한그릇"]
}
```

- `category` 값: 밥, 국/찌개, 면, 반찬, 일품, 분식/간식, 양식
- `difficulty` 값: 쉬움, 보통, 어려움

### 모듈 구성
- **레시피 저장소(Recipe Repository)**: `recipes.json`을 읽어 레시피 목록과 전체 표준 재료 목록(자동완성용)을 제공한다.
- **재료 정규화기(Ingredient Normalizer)**: 동의어 사전(예: 달걀→계란, 쪽파→대파)으로 사용자 입력을 표준 재료명으로 바꾼다. 앱 실행 중 LLM을 호출하지 않는다.
- **인덱서(Indexer)**: 레시피별로 "요리명 + 카테고리 + 주재료 + 태그" 텍스트를 만들어 임베딩하고 Chroma에 적재한다. 데이터 변경 시 한 번 실행하는 독립 명령으로 제공한다.
- **추천 엔진(Recommender)**: 앱의 핵심 모듈. 인터페이스는 "보유 재료 목록 + 보유 양념 설정 → 순위가 매겨진 추천 결과 묶음"이다.
  1. 정규화된 보유 재료로 벡터 검색해 후보 약 30개를 뽑는다.
  2. 후보마다 주재료 기준으로 `일치 재료`, `부족 재료`, `일치율`을 코드로 정확히 계산한다. 양념은 사용자가 체크 해제한 것만 부족 재료로 센다.
  3. 부족 재료 수 오름차순, 일치율 내림차순으로 정렬한다.
  4. "바로 가능(부족 0개)"과 "1~2개 부족" 두 묶음으로 나누고, 부족 3개 이상은 버린다. 묶음별로 상위 3~5개만 남긴다.
- **설명 생성기(Explainer)**: 최종 상위 레시피와 보유/부족 재료를 LLM에 넘겨 추천 이유와 대체 재료 제안을 생성한다. 판정(가능 여부, 부족 재료)은 하지 않고 설명만 한다. 실패하면 설명 없이 결과를 반환한다.
- **UI**: 재료 멀티셀렉트, 사이드바의 기본 양념 체크리스트, 결과 두 묶음의 레시피 카드(요리명, 카테고리, 시간, 난이도, 일치율, 부족 재료, LLM 설명, 펼침형 재료/조리 순서).

### 핵심 원칙
- **판정은 코드가, 설명은 LLM이 한다.** 이렇게 하면 레시피·재료 환각을 원천 차단하고 결과의 재현성을 보장한다.
- 기본 양념(소금, 설탕, 간장, 식용유, 후추, 참기름, 다진마늘 등)은 보유한 것으로 가정하는 것이 기본값이다.

## Testing Decisions

- 좋은 테스트란 외부에서 관찰 가능한 동작(입력 재료 → 추천 결과)만 검증하고, 내부 구현(정렬 함수 이름, 중간 자료구조)에는 의존하지 않는 테스트다.
- **테스트 경계(seam)는 추천 엔진 하나로 둔다.** 추천 엔진은 레시피 목록과 검색기(retriever)를 주입받는다. 테스트에서는 실제 Chroma/OpenAI 대신 "모든 레시피를 후보로 돌려주는 가짜 검색기"와 소규모 레시피 픽스처를 넣는다.
- 추천 엔진에서 검증할 동작:
  - 주재료를 모두 가지면 "바로 가능" 묶음에 들어간다.
  - 주재료 1~2개가 부족하면 "1~2개 부족" 묶음에 들어가고, 부족 재료명이 정확히 표시된다.
  - 3개 이상 부족하면 결과에서 빠진다.
  - 양념은 기본적으로 부족 재료로 세지 않지만, 사용자가 체크 해제한 양념은 센다.
  - 동의어로 입력해도(달걀) 표준 재료(계란) 레시피가 매칭된다.
  - 정렬 순서: 부족 수 오름차순, 그다음 일치율 내림차순.
  - 빈 입력과 매칭 결과 없음을 적절히 처리한다.
  - 설명 생성기가 실패해도 추천 결과는 반환된다.
- 데이터 무결성 검사: `recipes.json`이 100개이고, id가 고유하며, 필수 필드와 허용된 category/difficulty 값을 갖는지 확인한다.
- 테스트 프레임워크: pytest. 기존 코드베이스에 참고할 테스트는 없다(신규 프로젝트).
- LLM 출력 품질과 UI는 자동 테스트하지 않고 수동 시연으로 확인한다.

## Out of Scope

- 냉장고 사진 업로드 및 비전 모델 재료 인식 (향후 확장 후보. 입력 단계 앞에 붙이는 구조로 설계)
- 식약처 등 외부 레시피 API 연동
- 로그인/회원가입, 다중 사용자, 서버 배포
- 냉장고 재고 영구 저장 및 유통기한 관리
- Ollama 등 로컬 LLM 지원 (LangChain 구조상 교체는 쉬움)
- 영양/칼로리 정보, 레시피 이미지
- 장보기 목록 내보내기, 즐겨찾기, 평점

## Further Notes

- 원래 검토했던 "식약처 레시피 DB + LLM 재료 정규화" 방식은 직접 작성한 데이터셋으로 바꾸면서 폐기했다. 데이터를 처음부터 표준 재료명으로 쓰기 때문에 정규화 비용과 복잡도가 사라졌다.
- 레시피 100개 규모에서는 벡터 검색 없이 전수 매칭만으로도 충분히 빠르다. 그래도 과제의 RAG 실습 의도와 향후 데이터 확장을 고려해 벡터 검색 → 규칙 재정렬 구조를 유지한다.
- 동의어 사전은 `recipes.json`의 표준 재료 목록을 기준으로 작성하며, 사용자 입력은 자동완성으로 표준명을 고르게 해 사전 의존도를 낮춘다.
- 시연 안정성을 위해 인덱스는 미리 구축해 두고, 앱 실행 시에는 검색과 설명 생성만 수행한다.
